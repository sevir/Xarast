# Performance, memory and start-up gates for `cargo xtask perf`
# (phase 12 A4/A6, B2/B5, C2; story XARA-US-0061). docs/memory/perf.md,
# "CI gates", explains every choice below; change both together.
#
# Each gate is one metric of one `xarast-cli bench` scenario:
#
#   <id> <tiers> <metric> <limit> <scale> <budget> <reference> -- <bench args> [# note]
#
#   tiers      pr (every push, ci.yml job `perf`) and/or nightly
#              (perf-nightly.yml, which runs every gate)
#   metric     a key of the scenario's JSON `metrics` (lower is better);
#              times in ms, memory in MiB, growth in %
#   limit      the gate: the build fails above it (twice in a row)
#   scale      st | mt: the limit (and the budget) is multiplied by
#              max(1, this machine's calibration / the reference's), single-
#              threaded or all cores; none: memory, never scaled
#   budget     the product budget from docs/phases (reported, "-" if none);
#              a gate may sit above its budget when the budget is known to
#              be breached (the note names the task): it then catches
#              regressions until the task closes and the limit comes down
#   reference  the reference machine's measurement (perf.md), "-" if none
#
# `$CORPUS` is XARAST_XAR_CORPUS; those gates are skipped without it.
#
# Margins: a limit is the budget where the reference measurement is at
# most half of it; otherwise about 2x the reference for times and about
# 1.25x for memory. Times of a few milliseconds carry more.
